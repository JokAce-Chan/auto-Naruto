## 3. 识别功能的判断逻辑（当前版，完整描述）

对每一侧（左/右完全独立）依次执行：

1. **取 ROI**：从 `1280x150` 识别帧裁剪左/右区域。
2. **逐像素归类**：
   - 橙红/白突变 → 判“亮”（走 `EffectiveOrangeRange` 或“白色高光”规则 `r>=170 && g>=170 && b>=160`）；
   - 蓝族且为亮蓝核心（`r<=100 && b>=95 && b>=g && (b-r)>=35` 且 `b>=150 && g>=80 && (b-g)>=30`）→ 判“亮”；
   - 蓝族但非亮核心 → 判“暗”（暗蓝 / 深青暗格，含青蓝光晕）；
   - 灰绿背景 / 本底 → 忽略（不计入格）。
3. **找格**：列投影 → 聚簇 → 估间距（`DefaultSpacing=21`，超过 12–34 回退默认）→ 按格数 4/6 切分 → 按中心 X 升序排序。
4. **逐格分类**：在每格中心 `±Math.Clamp(spacing/4, 3, 5)` 的窄窗内统计“亮票 vs 暗票”，多数决定亮/暗。
5. **逻辑1 连续校验（本轮新增）**：
   - 左侧：亮格必须从**最左**连续，合法集合 `◆◇◇◇ / ◆◆◇◇ / ◆◆◆◇ / ◆◆◆◆`；出现 `◇◆◇◇、◇◆◆◇` 等“亮格左侧有暗格”→ 判噪声。
   - 右侧：亮格必须从**最右**连续，合法集合 `◇◇◇◆ / ◇◇◆◆ / ◇◆◆◆ / ◆◆◆◆`；出现 `◇◆◆◇、◇◆◇◆` 等“亮格右侧有暗格”→ 判噪声。
   - 违规处理：**不改变、不累加防抖**，保持上一稳定值；若无稳定基线则暂报占位值 `0`。预览小点按稳定值合成“连续亮块图案”（左侧前缀 / 右侧后缀），与数值一致、不闪烁。
6. **防抖提交**：合法新值需连续 `DebounceFrames`（默认 2）帧才提交为稳定值；首个合理读数立即立为基线。
7. **规则引擎**：只消费防抖后的稳定值；当该侧“恰好 -1”才启动/重置 `15.00s`；增、减≥2、加载中、同值均不动作。

### 3.1 值语义
- 合法读取时，`值 = 连续亮块长度`（左侧前缀长 / 右侧后缀长），与“亮格总数”相等。
- 非法（非连续）读取被逻辑1拦截，不参与取值。

## 6. 已知问题 / 限制（供下一轮优化）

1. **视频流延迟**：软件画面与游戏实时存在约 `1s` 延迟。这是 `screenrecord` 解码/传输开销，与识别准确度无关，属性能项。**已纳入下一轮优化范围。**
2. **“合法但错误”的连续形状**：逻辑1 只能拦截“位置错乱”形（`◇◆◇◇`、`◇◆◆◇`），无法识别“整行同时误判成另一张合法连续图”的情形（例如真实 `◇◇◆◆` 被误读为 `◆◆◆◆`）。**用户已确认当前该情况不存在，暂不实施“±1 步进 + 更长确认帧数”二次校验**；若后续真机复现再评估。
3. **预览小点 vs 稳定值**：已统一为“**跟随稳定值**”。违规帧由 `SnapStates` 按稳定值合成连续图案，不再显示实时原始误判图案；小点与数值一致、不闪烁。实时原始判定不再用于预览显示，仅取色/调试需要时另行开启。
4. **取色校准未接入蓝族判定**：当前蓝/橙判定用硬编码阈值，用户“取色校准”产出的 `BrightRange/DarkRange` 基本不参与蓝族分类，仅用于显示。若后续需要“按场景自适应阈值”，需重新设计接入方式。
5. **`DebounceFrames` 默认 2**：如需更强稳定，可调大，或改为按帧率自适应。
6. **置顶框（OverlayWindow）**：本轮只改主界面预览区；始终置顶的 OverlayWindow 位置/样式未动。若也需调整需另议。
